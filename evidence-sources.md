# Evidence Sources

## Why I Studied These Sources First

Before starting the investigation, I wanted to understand what evidence would be available in my Linux environment and what each source could actually tell me.

I did not want to begin searching through logs without understanding why I was looking at them. At this stage, my goal was to learn how to connect an investigation question with the appropriate source of evidence.

For example, if I need to investigate failed authentication attempts, I should know where that information is likely to be recorded. If I later need to understand what happened after a user gained access, I may need a different source of evidence.

This stage helped me understand an important principle that I will apply throughout the project:

> The question should guide the selection of the evidence source.

---

## Evidence Sources I Will Use

The following sources are relevant to the NorthWave Logistics laboratory environment.

| Source | What It Can Tell Me | Questions It Can Help Me Answer | Limitations |
|---|---|---|---|
| `/var/log/auth.log` | Authentication and authorization events, including successful and failed logins, SSH sessions, sudo activity, PAM events, and user switching | Who attempted to authenticate? From which IP? Was the attempt successful? When did it occur? Was sudo used? Were there repeated failures? | It does not necessarily show what a user did after authentication. Evidence may also be unavailable if logs were deleted or not properly configured. |
| `/var/log/syslog` | General system and service messages, including daemon activity, application errors, cron events, kernel messages, and other system events | Did a service restart? Were there unusual errors? What cron activity occurred? Was there an unexpected shutdown or reboot? | It can be highly noisy and contains events from multiple sources, so it requires filtering and context. |
| `auditd` logs | Security-relevant audit events such as command execution, access to sensitive files, identity changes, system calls, and configuration modifications | What actions were performed after access was obtained? Were sensitive files accessed? Were configurations modified? Was a suspicious binary executed? | It requires prior configuration, may generate a large volume of data, and cannot provide historical evidence if it was not collecting events at the time. |
| Service logs | Service-specific activity such as SSH connections or events generated by internal applications | What client connected? What resource was requested? Which user performed an action? Was there unusual service activity? | The format and available details depend on the service and its logging configuration. |
| Process and network information | Current processes, open ports, active connections, and runtime information obtained through tools such as `ps`, `ss`, `lsof`, and `/proc` | Is a suspicious process currently running? Is a process listening on an unusual port? Is there an unexpected active connection? | This information represents the current state of the system and is volatile. It does not provide historical information unless it was collected previously. |
| `cron` activity | Execution of scheduled tasks, typically recorded through system logging depending on the Linux distribution | What scheduled task executed? When did it run? Which user launched it? Did unusual scheduled activity appear? | It may show that a task executed without showing everything the executed script actually did. |

## Different Types of Evidence

One of the most important things I learned during this stage is that not all evidence is a historical log.

For this project, I can group the available evidence into three main categories:

| Evidence Type | Examples | Characteristics |
|---|---|---|
| Historical logs | `auth.log`, `syslog`, audit logs | They can help me reconstruct events that occurred in the past. |
| Current system state | Processes, network connections, `/proc` | This is volatile information that represents the current state of the system. |
| Configuration | `crontab`, `sshd_config`, user accounts | This provides semi-static operational and security context. |

Understanding this distinction is important because I may not always be able to answer an investigation question by searching historical logs in Splunk.

Depending on the question, I may need to examine logs, the current state of the system, or its configuration.

## How I Will Select an Evidence Source

During the investigation, I will use the question I am trying to answer to guide my choice of evidence source.

For example:

- **Question:** Were there failed authentication attempts?  
  **Possible source:** `/var/log/auth.log`

- **Question:** Did a service restart or generate unusual errors?  
  **Possible source:** `/var/log/syslog`

- **Question:** What did a user do after obtaining access?  
  **Possible source:** `auditd` logs, if available and properly configured

- **Question:** Is there currently a suspicious process or network connection?  
  **Possible source:** Current process and network information

This approach will help me avoid searching through data without direction and instead focus on finding evidence that is relevant to the question I am investigating.

## Project Decision

At this point, the primary evidence sources I will initially consider for this laboratory are:

- `/var/log/auth.log`
- `/var/log/syslog`
- Service-specific logs
- `cron` activity
- Current process and network information

I consider `auditd` a valuable source of evidence, especially when investigating actions performed after access has been obtained. However, it will remain optional at the beginning of the project and may be incorporated later if the investigation and laboratory environment require it.

The availability and usefulness of each source will be evaluated as the project progresses.

## What I Learned

One of the main things I learned during this stage is that different evidence sources provide different perspectives on the same environment.

Authentication logs can help me understand how access occurred. System logs can provide operational context. Audit logs may help explain what happened after access was obtained. Current system information can reveal what is happening at the time of collection.

I also learned that relying on a single source can provide an incomplete picture.

As I progress through the investigation, I will need to decide which source, or combination of sources, is most useful for answering the question I am currently investigating.

This is the main principle I am taking from this stage:

> Effective investigation begins with a question, and the question guides the search for evidence.
